# 诵经助手鸿蒙版移植开示功能和桌面卡片技术方案与开发计划

> 编写日期：2026-08-15  
> 对照工程：`/Users/yangxuehui/Documents/dev/GongKeAssistant`（macOS/iOS 版功课助手）  
> 目标工程：`/Users/yangxuehui/Documents/dev/Harmony/gongke_harmony`（Flutter + HarmonyOS 原生宿主）

> 产品范围确认（2026-08-15）：四种目标形态确认为“今日功课中卡、功课日历大卡、开示大卡、开示超大卡”；开示的收藏、完成、评论、TTS、分享和 JSON 导出均纳入本期；顺序模式当天固定，随机模式允许手动刷新换一条。

> 发布版本确认（2026-08-16）：当前准备发布为 **1.1.1（versionCode 111）**；`pubspec.yaml` 与 HarmonyOS `app.json5` 已同步。

## 1. 结论摘要

本次不是从零移植两个功能：鸿蒙版已经有开示录表、4 份内置 JSON、开示录/记录增删改页面，以及从文件选择器导入 JSON 的基本链路；真正缺少的是与 mac 版兼容的完整“开示文件”能力，以及供桌面卡片稳定消费的数据层。

推荐方案如下：

1. **开示业务继续放在 Flutter/Drift 中实现**，补齐 JSON 兼容、事务导入、导出、记录状态、今日开示计算及深链跳转。
2. **桌面卡片使用 HarmonyOS 原生 ArkTS Form Extension 实现**。Flutter 页面不能直接作为系统桌面卡片运行；卡片 UI、生命周期、刷新和点击事件应由 ArkTS 管理。
3. **Flutter 主应用生成版本化 JSON 快照，ArkTS 卡片只读快照**。卡片不直接访问 Drift/SQLite，避免数据库并发、Dart 引擎不可用和生命周期受限问题。
4. mac 版所称“四个小组件”按用户可见形态迁移为：
   - 今日功课中卡；
   - 开示大卡；
   - 开示超大卡（鸿蒙没有 `systemExtraLarge` 同名规格，需映射或合并）；
   - 功课日历大卡。

HarmonyOS 标准卡片规格为 `1*2`、`2*2`、`2*4`、`4*4`。建议首期以 **3 个卡片定义、4 种规格/形态**落地：今日功课 `2*4`、开示 `4*4`（另评估 `2*4` 紧凑版）、功课日历 `4*4`。mac 版“开示超大卡”不能机械一比一复制，应在平板真机确认鸿蒙宿主提供的规格后决定是共用 `4*4` 响应式布局，还是增加平板专属展示。

## 2. 现状分析

### 2.1 mac 版开示能力

mac 版主要模型为 `TipsBook` 和 `TipsRecord`：

- 开示录字段包括名称、说明、Base64 图片、类型、版本、创建时间、优先显示时间、产品 ID。
- 开示记录字段包括 JSON ID、正文、收藏时间、完成时间、标签、评论和排序时间。
- 支持内置数据初始化、开示录和记录的增删改、优先显示、每日轮播、收藏/完成、评论、TTS、分享、JSON 导入导出。
- 主应用把开示 JSON 复制到 App Group，小组件可独立按开示录、顺序/随机模式计算显示内容。
- 卡片点击后通过 URL Scheme 定位开示录及具体记录。

### 2.2 mac 版小组件构成

代码层面 `MyWidgetBundle` 注册了 3 个 Widget：

| Widget | 用户可见形态 | mac/iOS 尺寸 | 数据 |
|---|---|---|---|
| `GongKeMediumWidget` | 今日功课 | `.systemMedium` | 当日功课文本和完成状态 |
| `GongKeLargeWidget` | 开示语录 | `.systemLarge`、`.systemExtraLarge` | 开示正文、书名、图片、日期、刷新时间 |
| `GongKeCalendarWidget` | 功课日历 | `.systemLarge` | 三个月功课完成度快照 |

因此“当前有四个小组件”是指四种可添加的展示形态，而不是四个代码注册项。用户提供的 mac 桌面截图已确认其从左到右分别为：

1. 今日功课中卡：左侧日期和应用图，右侧显示今日功课完成结果；
2. 功课日历大卡：顶部标题和日期，下方显示整月完成状态；
3. 开示大卡：图片和日期在顶部，正文适配较窄的大卡；
4. 开示超大卡：与开示大卡信息相同，但利用横向空间展示更长正文。

鸿蒙版应保持相同的信息层级和视觉识别，但按鸿蒙 `2*4`、`4*4` 卡片尺寸重新排版，不强求像素级复制 mac 的横向比例。

### 2.3 鸿蒙版已有开示能力

已有内容：

- `TipBook`、`TipRecord` Drift 表；
- `assets/tips/1.json` 至 `4.json` 内置开示文件；
- 开示录列表、新增/修改/删除、优先显示；
- 开示记录列表、新增/修改/删除；
- 文件选择和 `.json` 导入入口；
- `getCurrentRecord()` 按开示录优先级取得当前记录。

主要差距和问题：

| 项目 | 当前鸿蒙版 | 目标 |
|---|---|---|
| JSON 解析 | 动态 Map 强制取值，字段缺失易运行时异常 | 明确 DTO、版本、默认值和错误信息 |
| 重复判断 | 用“文件名”比较数据库“书名”，且批量导入时列表不更新 | 用规范化书名/稳定 ID；批次内也去重 |
| 原子性 | 单本失败会手工回滚，批量导入非完整事务 | 单本事务；明确批量部分成功策略 |
| 记录字段 | 只持久化正文及通用备注/创建时间 | 补齐 `jsonId`、收藏、完成、评论、标签等必要字段 |
| 开示录字段 | 缺少版本、来源类型、产品 ID 等 | 至少补齐格式版本和来源；收费字段按产品范围决定 |
| 导出 | 无 | 导出兼容 mac 版的 JSON |
| 今日开示 | 仅简单轮取，未形成稳定快照 | 统一顺序/随机规则、起始日期、记录标识和空状态 |
| 分享/TTS | 分享首版关闭；开示页未完整对齐 | TTS 可优先恢复；分享另列平台适配任务 |
| 卡片同步 | 无 | 主应用写快照并通知 Form 刷新 |
| 深链定位 | 无卡片链路 | 卡片点击打开功课页或指定开示记录 |

### 2.4 鸿蒙工程现状

- 当前 `ohos/entry/src/main/module.json5` 只声明 `EntryAbility`，没有 `FormExtensionAbility`。
- 原生层已有多个 Flutter MethodChannel 插件，可沿用同样模式新增卡片桥接插件。
- `shared_preferences_ohos` 适合轻量配置，但不应把大尺寸 Base64 图片和整本开示长期塞入 Preferences。
- 功课和开示的权威数据源均在 Flutter/Drift，ArkTS 侧不应重复建一套业务数据库。

## 3. 功能范围建议

### 3.1 第一阶段必须包含

- 兼容 mac 版 JSON 的开示文件导入和导出。
- 开示录及开示记录完整 CRUD。
- 开示录优先显示；记录收藏、完成和评论。
- 开示 TTS、分享和 JSON 导出。
- 今日开示的顺序模式和随机模式。
- 3 个 HarmonyOS 卡片定义：今日功课、开示语录、功课日历。
- 4 种目标形态：`2*4` 今日功课、`4*4` 开示、平板开示等价形态、`4*4` 日历。
- 主应用写快照、主动刷新、卡片空状态和点击跳转。
- 浅色/深色模式、中文资源、真机加桌验证。

### 3.2 建议延后

- 卡片内直接收藏、完成或编辑功课（涉及 `message/call` 事件及后台拉起）。
- 云端导入、跨设备自动同步。
- 卡片内切换月份。
- 开示收费产品字段和购买逻辑。
- 锁屏卡片、待机屏保卡片、Push 刷新。
- 与 mac 版跨平台自动同步数据库；本期只保证 JSON 文件互导兼容。

## 4. 开示文件技术方案

### 4.1 统一 JSON 协议

保留 mac 版顶层结构以兼容已有文件：

```json
{
  "schemaVersion": 1,
  "quotation": {
    "id": "optional-stable-id",
    "name": "广钦老和尚开示",
    "remarks": "来源说明",
    "image": "base64-or-empty",
    "ver": "1",
    "records": [
      {
        "id": "1",
        "content": "开示正文",
        "isFavorite": false,
        "completedDate": null,
        "comments": ""
      }
    ]
  }
}
```

兼容原则：

- `schemaVersion`、`quotation.id`、`ver` 和记录状态均允许缺省，以兼容旧文件。
- `quotation.name`、`records`、`record.content` 为必填；错误需要指出文件名和字段路径。
- 未知字段忽略，便于未来扩展。
- 图片允许空字符串；非空时校验 Base64 和解码后体积，建议单图上限 2 MiB。
- 对名称和正文做首尾空白规范化，但不擅自改动正文内部换行。
- 导出使用 UTF-8、稳定字段名；日期统一 ISO 8601。

建议新增纯 Dart 类型：`TipBookFileDto`、`TipBookDto`、`TipRecordDto`、`TipFileCodec`，UI 和数据库层不再直接访问动态 Map。

### 4.2 Drift 数据迁移

建议升级数据库 schema，并在 `TipBook` 增加：

- `sourceId`：文件内稳定 ID，可空；
- `version`：开示文件版本，可空；
- `sourceType`：`builtin/imported/userCreated`；
- `updatedDateTime`：便于覆盖导入和同步快照。

在 `TipRecord` 增加：

- `jsonId`：文件内记录 ID；
- `favoriteDateTime`；
- `completedDateTime`；
- `comments`；
- `tag`；
- `sortOrder`：不要仅依赖自增 ID 表示文件顺序。

同时为 `bookId` 建索引；删除开示录时在事务中级联删除记录。若 Drift 当前版本和鸿蒙 SQLite 后端不方便建外键级联，保留显式事务删除。

### 4.3 导入流程

```text
文件选择器
  → 读取字节并校验 UTF-8/大小
  → TipFileCodec 解码和字段校验
  → 生成导入预览（书名、记录数、重复状态）
  → 用户确认冲突策略
  → Drift transaction 写入书和记录
  → 重算今日开示
  → 写卡片快照并请求刷新
```

冲突策略建议首期提供：

- 同稳定 `sourceId`：提示“跳过”或“覆盖”；
- 无稳定 ID 但规范化书名相同：提示“跳过”或“另存为”；
- 默认选“跳过”，避免静默覆盖用户编辑。

现有“文件名等于书名”的判断必须移除。批量导入采用“每本一个事务”，最终报告成功、跳过和失败清单；这样一个坏文件不会回滚其他有效文件。

### 4.4 导出流程

- 从 Drift 查询一本开示录及按 `sortOrder` 排序的记录。
- 转为统一 DTO，保留收藏、完成、评论及 JSON ID。
- 生成 `<开示录名称>.json`，调用 HarmonyOS 文件保存/系统分享能力。
- 增加“导出后重新解码”测试，确保 round-trip 不丢字段。

### 4.5 今日开示规则

把规则收敛到单一 `TodayTipService`：

- 开示录排序：优先显示时间倒序，其次创建时间/`sortOrder`。
- 顺序模式：以用户首次启用日期与当前本地日期的日差，对合并后的记录数取模。
- 随机模式：卡片每次手动刷新可换一条；自动刷新当天保持稳定，建议用 `yyyy-MM-dd + cardInstanceId` 生成确定性随机种子。
- 空记录、记录被删除、时区变化均返回显式空状态，不抛异常。
- 快照必须包含稳定的 `bookId/sourceId + recordId/jsonId`，禁止用正文前 100 字作为唯一标识。

### 4.6 TTS 与分享

TTS 继续复用鸿蒙版已有的 `OhosTtsPlugin`/`tts_tools.dart`，在开示预览和记录详情页提供播放、暂停/停止以及页面销毁时释放。长文本按平台限制分段播放，避免一次提交过长导致失败。

分享纳入本期，推荐采用“Flutter 生成内容，ArkTS 拉起系统分享面板”的桥接方案：

```text
Flutter 开示页面
  → 生成纯文本或分享卡片 PNG
  → HarmonySharePlugin（MethodChannel）
  → HarmonyOS Share Kit 系统分享面板
```

分享形态分两级实现：

1. **必须实现：纯文本分享**。内容包括开示正文和书名，适合消息、邮件和备忘录等目标应用。
2. **必须实现：图片分享**。复用/补齐当前分享卡片页面，在 Flutter 侧将卡片渲染为 PNG，保存到应用缓存；ArkTS 侧通过安全可访问的文件 URI 和准确的 UTD 类型交给 Share Kit。
3. JSON 文件的“分享”与“导出保存”复用同一份编码结果，但入口语义分开：导出由用户选择保存位置，分享则拉起系统分享面板。

实现时需要：

- 根据当前目标 SDK 接入 Share Kit，并使用精确 UTD 类型，不使用笼统的 `*/*`；
- 验证纯文本、PNG 和 JSON 三类数据在手机真机上的目标应用匹配；
- 分享完成或取消后清理临时图片/JSON，保留失败重试所需的短期缓存；
- 分享失败不影响开示数据，错误提示区分“平台不支持、没有可接收应用、文件 URI 无权限、用户取消”；
- 不把系统“分享面板”和 mac 的 App Group/卡片共享数据混为一套通道。

## 5. HarmonyOS 卡片技术方案

### 5.1 原生 Form Extension

在 `ohos/entry` 新增：

```text
src/main/ets/formability/
  GongKeFormAbility.ets
src/main/ets/widget/
  TodayTasksCard.ets
  TodayTipCard.ets
  GongKeCalendarCard.ets
src/main/ets/widget/model/
  WidgetSnapshot.ets
  WidgetSnapshotRepository.ets
src/main/resources/base/profile/
  form_config.json
```

并在 `module.json5` 注册 `FormExtensionAbility` 和卡片元数据。ArkTS 是 HarmonyOS 官方推荐的卡片实现方式；支持规格应以目标 SDK 实际 `form_config.json` 校验结果为准。

### 5.2 数据边界

推荐数据流：

```text
Flutter UI / Drift
       │ 数据变更或应用回前台
       ▼
WidgetSnapshotService（Dart）
       │ MethodChannel：writeAndRefresh(snapshotJson)
       ▼
HarmonyWidgetPlugin（ArkTS）
       │ 原子写入应用沙箱共享文件
       │ formProvider.updateForm / 请求刷新
       ▼
FormExtensionAbility → ArkTS 卡片 UI
```

关键约束：

- 卡片只读取快照，不打开 Drift 数据库，也不依赖 Flutter Engine 常驻。
- 写文件采用“临时文件 + 替换”或平台原子写能力，防止卡片读到半截 JSON。
- 快照只保存展示必要信息，图片转为独立压缩文件路径，不在 JSON 中反复存 Base64。
- 所有快照带 `schemaVersion`、`generatedAt`、`timeZone`；解析失败回退空状态。
- ArkTS 与 Flutter 是否能直接读取同一应用沙箱文件，应在 Spike 中真机验证；若隔离，则由原生插件写入 Form Extension 可访问目录或使用平台 Preferences 仅存小 JSON/路径。

### 5.3 快照协议

建议使用一个总索引和三个业务快照：

```text
widget/index.json
widget/today_tasks.json
widget/today_tip.json
widget/calendar.json
widget/images/tip_<hash>.jpg
```

`today_tasks.json`：

- 日期、更新时间；
- 最多 5 条任务：名称、目标、完成标志；
- 是否有更多、是否过期。

`today_tip.json`：

- 开示录和记录稳定 ID；
- 书名、正文、评论；
- 本地压缩图片路径；
- 今日日期、更新时间、显示模式。

`calendar.json`：

- 沿用 mac 版已验证的数据口径：schema、生成时间、时区、范围起止；
- 日期到 `plannedCount/completedCount` 的映射；
- 生成上月、当月、下月三个月滚动快照。

### 5.4 三类卡片设计

#### A. 今日功课卡（`2*4`）

- 左侧日期、星期和应用图标；右侧最多 5 条今日功课。
- 完成项打勾，未完成项显示空框；超出显示“…” 。
- 快照不是今天时显示“请打开诵经助手更新今日功课”。
- 点击卡片打开 Flutter 功课首页。

#### B. 开示语录卡（首期 `4*4`）

- 顶部图片、日期、书名/更新时间；主体显示开示正文。
- 复刻 mac 版的数据职责：主应用把书目、完整开示记录和显示模式写入卡片扩展可访问的 `today_tip_catalog.json`，卡片不启动 Flutter Engine 即可自行选取。
- 顺序模式按开始日期和当天日期固定记录，点击刷新不换；随机模式的系统/应用自动刷新保持当前记录，只有点击刷新才递增卡片实例自己的刷新序号、重新选取并避开当前记录。
- 点击打开开示页并定位具体记录。
- mac 的 `.systemExtraLarge` 在鸿蒙侧不具备同名尺寸。首期用 `4*4` 响应式布局覆盖手机和平板；完成 Spike 后再决定是否需要独立平板卡片配置。

#### C. 功课日历卡（`4*4`）

- 顶部显示图标、当前日期、更新时间；下方显示当月日历。
- 无计划显示日期/农历；有计划未完成显示黄色 `todo`；部分或全部完成显示绿色百分比；今天蓝色描边；周末红字。
- 农历计算可由 Dart 写入快照，避免 ArkTS 与 Flutter 使用不同历法库产生差异。
- 点击打开功课日历页，首期不在卡片内切月或勾选。

### 5.5 跳转协议

建议不要复制 mac 的 `myapp://page2/<书名>/<正文前100字>`，改用稳定参数：

```text
gongke://tasks?date=2026-08-15
gongke://tips?bookId=<id>&recordId=<id>
gongke://calendar?month=2026-08
```

ArkTS `router` 事件携带参数打开 `EntryAbility`，`EntryAbility` 通过 MethodChannel 把启动参数交给 Flutter；Flutter 在 Navigator 就绪后消费一次。需要处理冷启动、热启动、参数缺失和目标记录已删除四种情况。

### 5.6 刷新策略

- 主应用启动完成、回到前台、功课计划/完成状态变化、开示导入/编辑/删除/排序变化时写对应快照并主动请求刷新。
- 卡片配置使用系统允许的被动刷新作为兜底；不要依赖 30 分钟或 60 分钟一定准时执行。
- 跨日时卡片可根据系统日期显示“数据过期”；下次系统刷新或打开主应用后更新。
- 只刷新受影响的卡片类型，避免每次开示变化都重绘日历。
- 保存卡片实例 ID；删除卡片时清理实例级配置。

## 6. 风险与验证点

| 风险 | 影响 | 应对 |
|---|---|---|
| 当前 Flutter OHOS SDK 与 Form Kit API 版本不匹配 | 无法编译或配置字段不同 | 第一项先做最小卡片 Spike，确认 SDK/API/真机 |
| Flutter 与 Form Extension 沙箱可见性 | 卡片读不到快照 | 原生插件统一写入；Spike 验证路径和权限 |
| 后台启动 Flutter Engine 不可靠 | 刷新按钮不能即时换开示 | 默认每日稳定内容；刷新由 ArkTS 本地候选数据完成或降级 |
| Base64 图片过大 | 导入卡顿、数据库和卡片内存高 | 导入限额、解码压缩、卡片存缩略图文件 |
| JSON 旧格式不一致 | 用户已有文件导入失败 | 宽松解码、严格语义校验、逐文件错误报告 |
| 数据库迁移失败 | 用户开示数据损坏 | schema migration 测试、迁移前备份、仅增列不破坏旧列 |
| “四个”定义理解不同 | 验收范围偏差 | 开发前确认下文 3 个产品问题 |
| 鸿蒙卡片刷新受系统调度 | 内容不即时 | 主动刷新 + 过期提示 + 被动刷新三层策略 |
